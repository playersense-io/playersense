# Native libraries

This folder is empty in the repository and filled by a release step:

```bash
cd sdk && ./build-native.sh && cd unity && ./install-plugins.sh
```

The binaries are not committed. An unstripped iOS static library is 21 MB against roughly
550 KB of linked code, and eight platforms of that would dominate the repository. A checkout
of the monorepo builds them; a published UPM package ships them.

## What goes where

| Path | Built from | Notes |
|---|---|---|
| `iOS/libplayersense.a` | `aarch64-apple-ios` | Static. Linked into the app binary, which is why `DllImport` names `__Internal` on iOS |
| `macOS/libplayersense.dylib` | both `*-apple-darwin`, `lipo`'d | Serves the Editor and the player, Apple silicon and Intel |
| `Android/arm64-v8a/libplayersense.so` | `aarch64-linux-android` | |
| `Android/armeabi-v7a/libplayersense.so` | `armv7-linux-androideabi` | 32-bit; still required by Google Play for some device sets |
| `Android/x86_64/libplayersense.so` | `x86_64-linux-android` | Emulators, Chromebooks |
| `Windows/x86_64/playersense.dll` | `x86_64-pc-windows-msvc` | No `lib` prefix: Windows convention |
| `Linux/x86_64/libplayersense.so` | `x86_64-unknown-linux-gnu` | |

WebGL is absent on purpose. The core compiles for `wasm32-unknown-unknown`, which proves it
does no I/O of its own, but Unity WebGL needs a static library for `wasm32-unknown-emscripten`
built against the exact Emscripten version that Unity ships. That is a separate piece of work.

## Import settings

You do not configure these. `Editor/PlayerSensePluginImporter.cs` sets every plugin's platform
from its folder on load, and rewrites the `.meta` when it does not already match.

It exists because Unity's own guess is wrong. Measured on a machine with the iOS module not
installed, `iOS/libplayersense.a` imported as **Any Platform** with iOS itself unticked — a
static library offered to Windows, Android and Linux builds and withheld from the one platform
it is for. A committed `.meta` would not fix that either: the binaries are a release artifact,
so the `.meta` is generated by whichever machine ran `install-plugins.sh`, and that machine
generates the wrong one unless it happens to have every platform module installed.

What the rule says, and why each half matters:

- **iOS is not ticked for the Editor.** The Editor cannot load a static library, and a tick
  there is a startup error on every domain reload.
- **macOS is ticked for the Editor** as well as for standalone macOS, or nothing works in play
  mode.
- **Android libraries carry their ABI** (`ARM64`, `ARMv7`, `X86_64`), from the folder Android
  itself names them by. Getting this wrong ships an APK that installs and then crashes on the
  first `Track`.
- **Nothing is ever Any Platform.**

A folder the rule does not recognise is left alone and logs a warning naming itself, rather
than being guessed at — guessing is what this replaced.

The `.meta` files it writes **are** committed, even though the binaries are not. They carry the
settings, and the script re-checks them on every load, so a wrong one self-heals rather than
shipping.

## The check that matters

`build-native.sh` asserts that the shared library exports **only** `ps_*` symbols. Two
Rust-based SDKs linked into one iOS binary otherwise collide on their `__rust_*` symbols, and
the failure is a link error in someone else's project, weeks later.
